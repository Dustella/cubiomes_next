# 26.2 structure calculations

## Starting point

The Cubiomes-facing structure API covers the 26 release entries from 1.0 through 1.21.4. Its native-oracle results do **not** establish 26.2 compatibility. This document was written before the 26.2 experiments; the implementation and evidence recorded below are a separate, data-driven path, never an alias to Cubiomes 1.21.4 or its biome tree.

The baseline for new behavior is the local stable 26.2 official runtime (world version 4903, Java 25). Unchanged Cubiomes behavior is reused only where comparison establishes that it still applies.

## Clean-room and repository boundary

- Official jars, mappings, extracted JSON, class listings, decompiled sources, and generated official-world outputs stay under the existing external `../official_source/26.2/` directory or ignored `gt-out/` / `bundles/` directories. None may be checked in.
- Prefer declarative worldgen data and black-box calls to the official runtime. Inspect official implementation behavior only where data and runtime observations do not explain a rule.
- Checked-in implementation is independently written. No official source/decompiled instruction fragments are copied into TypeScript, C, comments, examples, patches, or documentation.
- Checked-in oracle tools may invoke public official APIs; they must not embed game method bodies. Observations recorded here are behavioral descriptions, not code transcriptions.
- Keep origin and licensing distinct: MIT Cubiomes source, our implementation, local official data, and WASI runtime notices are not interchangeable.

## Questions to resolve experimentally

1. Enumerate 26.2 structure sets, placements, structures, biome tags, dimensions, and enabled presets. Identify additions/removals and changed salts, spacing, separation, spread, frequency reduction, or exclusion rules.
2. Check exact candidate placement, including negative region/chunk coordinates, full signed-long seeds, weighted structure selection, and concentric stronghold rings.
3. Check biome validation against the 26.2 biome source, including new biomes and Nether climate changes. Distinguish biome eligibility from terrain-dependent start generation.
4. Identify which start variants, terrain checks, and recursive layouts remain compatible with the existing baseline. Unsupported calculations must remain explicitly unsupported rather than return old-version answers.
5. Run the actual worker path. CPU-intensive generation stays off the caller thread; do not add a GPU implementation merely for placement arithmetic.

## Acceptance and reporting

- Exercise the official runtime before claiming an algorithm or compatibility result; do not infer support from identical-looking metadata alone.
- Compare deterministic candidate/start results across multiple seeds, signed-long extrema, negative coordinates, and all relevant dimensions/placement families.
- Preserve existing 1.0–1.21.4 behavior and worker lifecycle contracts.
- Make any new version or data requirement explicit in the API. Local official-derived bundles remain local inputs, not vendored assets.
- Report separate statuses for candidate placement, weighted selection, biome checks, terrain/start generation, variants, and piece layouts. A candidate or accepted biome is not proof that a complete structure generates.

## Evidence record

The experiment now provides a runnable `BundleStructureWorker`, backed by a local `structure-bundle-1` input: **20 structure sets and 34 structure definitions**. It uses the existing 26.2 CPU biome model and all heavy work stays inside the dedicated worker. These new calculations are TypeScript/f64 in that worker, not a claim that the old Cubiomes WASM understands 26.2. The existing WASM backend and version resolver remain unchanged for 1.0–1.21.4.

### Verified scope

| Calculation | Status |
| --- | --- |
| Structure/biome-tag/preset catalog | Verified against the official registries in all tested worlds |
| Random-spread candidates | Verified for all 19 sets, including linear/triangular spread and negative coordinates |
| Frequency and exclusion gates | Verified; exclusions use other **placement** candidates, not actual generated starts |
| Weighted retry order | Verified against the official dispatcher while an observer deliberately makes earlier starts fail |
| Stronghold rings | Full preferred-biome-adjusted positions, verified against official ring positions |
| Explicit quart-point biome eligibility | Verified against the actual 26.2 biome source and allowed-biome holders |
| Terrain-dependent generation starts | Official oracle experiments only; **not implemented in the worker API** |
| 26.2 start variants and recursive piece layouts | **Not provided by this API**; no old-version fallback |

The catalog advertises `generationStarts: false`, `terrain: false`, and `pieces: false`. Do not promote a placement pass, a retry order, or eligibility at a requested biome point to a complete generated structure.

This experiment covers the actual structure registry and its structure sets. It does not add 26.2 decorator calculations for desert wells, geodes or small End island decoration; those are separate from these structure sets.

### Observed behavior that matters

- Whole structure sets are filtered by source-wide biome overlap. Entries inside an active set are **not** individually removed from weighted retries. In the Overworld, an impossible Nether portal entry still occurs in the official forced-failure retry sequence. `activeStructures` is eligibility metadata, not a replacement weighted list.
- Frequencies use Java float precision. Legacy reducer variants use different seeding and draw rules, and the default reducer's salt/X/Z ordering differs from ordinary placement seeding. Synthetic whole-placement public API probes, not a guessed formula, verified those details.
- Outpost exclusion is an inclusive chunk square and checks the village set's full placement gate. It does not wait for a village's terrain/biome generation to succeed.
- Each stronghold ring point uses a separately forked RNG for the preferred-biome search. The worker samples the 26.2 biome bundle; it does not use the older Cubiomes tree. Nether/End states do not expose Overworld stronghold rings.
- The registry includes `nether_fossils`, absent from the old numeric Cubiomes structure API. All 20 official sets are represented; multiple structure variants retain their original entry order and weights.

### Reproduction

Use local official data and the existing local 26.2 biome bundle. Official-derived structure data stays ignored:

```sh
bun run bundle:structures --data ../official_source/26.2/gen/data/minecraft --biomes bundles/26.2.bundle.json --out bundles/26.2.structures.bundle.json
bun run structure26-fixtures --server-dir ../official_source/26.2
bun run build:structures
bun run check:structure26
bun run check:structures
bun run typecheck
bun test
bun run serve:verification
```

The bundle builder reads JSON registry data and resolves biome tags; it never reads official method bodies. It requires a 26.2-labeled biome bundle and supported placement families; supply registry data from the same official build. The worker rejects mismatched biome/structure version labels. A fresh checkout needs locally generated official data/bundles for these checks, but no such input is compiled into `public/structure-worker.js`.

`tools/gt/GtStructures26.java` loads actual vanilla pack resources and bound worldgen tags through public APIs. The vanilla-registry bootstrap alone leaves biome holders unbound and is insufficient for structure validation. The Java harness invokes official placement/ring/biome/dispatcher/generation APIs; it does not implement their algorithms.

### Library usage

```ts
import { BundleStructureWorker } from './src/structures';

const worker = await BundleStructureWorker.create(
  { seed: 12345n, dimension: 'overworld', preset: 'normal' },
  { bundle: '/bundles/26.2.structures.bundle.json' },
);
try {
  const catalog = await worker.execute({ op: 'catalog' });
  const candidates = await worker.execute({
    op: 'scan', set: 'minecraft:villages',
    regionX: -4, regionZ: -4, width: 8, height: 8,
  });
  const rings = await worker.execute({ op: 'rings' });
  const point = await worker.execute({
    op: 'biome', structure: 'minecraft:village_plains',
    qx: 0, qy: 16, qz: 0,
  });
} finally {
  worker.terminate();
}
```

The default worker URL is `/structure-worker.js`; `workerURL` can be overridden. URL bundles are fetched and parsed inside the worker. Bun callers can pass an already parsed `StructureBundle` and a `file:` URL for the built worker. Both clients share message correlation, error handling and termination, but do not share version assumptions or structure-ID namespaces.

- `set` and `structure` are registry IDs, not the numeric Cubiomes type IDs. Missing `minecraft:` is normalized on requests; bundle registry keys are fully qualified.
- `position`/`scan` address structure **regions**. Results carry both chunk coordinates and block/locate coordinates. The local set's spacing determines region size.
- `initialCandidatePass` means the returned potential chunk is the region's initial candidate. `frequencyPass`, `exclusionPass`, `dimensionPass` and `placementPass` describe separate gates. `exclusionPass: null` means it was not evaluated.
- `attemptOrder` is empty for failed placements. Otherwise it is the order if every previous start fails, **not** the final chosen structure.
- `rings` positions are biome-adjusted, not approximate ring centers. Pagination is zero-based; inactive dimensions report no positions.
- `biome` samples an explicitly supplied **quart coordinate** (four blocks per unit). Its scope is `explicit-quart-point-not-generation-start`; it does not calculate a structure's true terrain-dependent sampling position.
- Bounds: scans at most 16,384 regions, block-space bounds ±30,000,000, at most 128 ring positions, and point quart Y between -512 and 512. Invalid inputs reject without silently switching backends.
- Preserve the `.structures.bundle.json` suffix: biome-only discovery excludes these inputs. The Vapor atlas now exposes candidate overlays when both local 26.2 bundles exist; its ring overlay is explicitly limited to the first 16 positions. The library API retains full 128-position support and the generation limitations above.

### Exercised verification

The matrix covers 17 worlds: five seeds (0, -1, 12345, signed-long minimum/maximum) in three dimensions, plus Overworld large-biomes and amplified presets.

| Comparison | Cases | Mismatches | Errors |
| --- | ---: | ---: | ---: |
| Bun worker vs official API | 3,740 | 0 | 0 |
| Attached Chromium worker vs official API | 3,740 | 0 | 0 |
| Four reducer methods vs whole-placement API | 4,200 | 0 | 0 |
| Existing 1.0–1.21.4 worker vs native Cubiomes | 3,658 | 0 | 0 |

The new matrix contains 17 catalogs, 1,938 positions, 1,734 point-biome checks, 17 complete ring results, and 34 multi-region scans. Authored constant-climate datapack regressions additionally cover unfiltered weighted entries, dimension eligibility, frequency-zero failure and exclusion dependence on the other set's frequency. The full suite passed 36 tests; type checking passed.

A cold full-ring browser request matched the official 128 positions while the caller continued processing MessageChannel events. An invalid random-spread request for the rings family rejected cleanly, subsequent ring generation recovered on the same worker, and termination rejected all queued callers. Ring searches can take seconds on the first request; pagination computes and caches only the required prefix.

Official start feasibility was also run, **outside the worker implementation**, using actual noise terrain and the original biome predicates. For buried treasure, mineshafts and fortresses, 713 candidates first passed official placement checks: 58 yielded valid starts and 655 did not, with no errors. Another 85 direct start probes yielded 9 valid and 76 invalid starts. These non-template probes are not template-backed generation, block placement, chunk population, or proof that every structure's start/terrain rules are implemented.
